# Client Requirements Compliance Audit

Source: "Dental Clinic Management System — Client Requirements"

Audit date: 2026-09-18
Audit branch: `codex/client-requirements-audit`
Base commit: `72f5701`

## Status definitions

- **Met**: implemented end to end, with an enforceable backend path and usable UI.
- **Partial**: important pieces exist, but at least one required field, workflow step, permission, notification, or concurrency guarantee is missing.
- **Gap**: the required workflow is not implemented.
- **Client decision**: implementation depends on a requirement the client explicitly left open.

## Executive result

The current product is **partially compliant**. It now implements the client's atomic queue claim, payment attribution/concurrency protection, and explicit six-month recall record and SMS-delivery workflow. A dedicated doctor workspace, the patient-facing feedback delivery flow, complete inventory purchasing, and several API permission boundaries remain incomplete.

## Highest-risk findings

1. **UI role hiding is not authorization.** Several sensitive endpoints authenticate but do not pass allowed roles to `requireAuthAndRole`, including inventory reports/transactions.
2. **Live recall delivery still depends on deployment configuration.** The workflow is implemented, but a production Ethiopian SMS provider and daily external invocation of the protected cron endpoint must be configured and acceptance-tested.
3. **Feedback delivery is incomplete.** Submission and analytics exist, but no patient-facing page/token plus post-treatment SMS workflow exists.
4. **Expiration notifications are insights rather than assigned notifications.** The daily job does not yet create configurable, responsible-user alerts for expiring batches.

## Implementation progress

Completed on `codex/client-requirements-audit`:

- Atomic doctor claim with a single-winner compare-and-set and assignment timestamp.
- Doctor-only `Take Patient` UI action and queue navigation entry.
- Generic appointment-update bypass prevention and all-doctors filter correction.
- Payment recorder/provider persistence, Telebirr/Other methods, and atomic invoice balance posting.
- Admin-only, clinic-scoped survey-result access.
- Six-month recall records derived from completed treatments, with configurable reminder lead days and returned/cancelled lifecycle states.
- Atomic reminder claiming, bounded retry/recovery, SMS log linkage, Ethiopian phone normalization, and Addis Ababa send-hour enforcement.
- Regression tests for queue claims, claim conflicts, queue filtering, payment attribution, payment conflicts, and survey isolation.
- Regression tests for recall date calculation, duplicate prevention, return tracking, Ethiopian SMS validation, and concurrent cron execution.

## Recommended delivery order

1. Queue model, atomic claim endpoint, role enforcement, doctor queue/assigned view, and concurrency tests.
2. Payment attribution/provider schema, atomic posting, financial permission projection, and tests.
3. Configure and live-test the recall scheduler/SMS provider, then add aggregate recall reporting and an end-to-end patient-journey test.
4. Feedback public link/token, post-treatment SMS trigger, results authorization, then the client-selected GoodDoc integration.
5. Inventory expiration configuration, responsible-user notifications, purchase-order workflows/history, and store-role permissions.
6. Cross-device and full patient-journey acceptance tests.

## Client decisions still required

- What GoodDoc is in this clinic's workflow and whether it provides an API or only a review URL.
- Exact financial fields doctors may see and which doctors may see them.
- Final role/permission matrix, including whether a dedicated inventory/store role is required.
- Per-event notification channels and responsible recipients.
- Default/configurable expiration-warning lead time and recall reminder lead time.
